# 09 — Contributing

Conventions that keep a two-app monorepo with a shared database from drifting, plus an
honest list of the debt you will meet.

---

## 1. Before you start

1. Read [01 Getting started](01-getting-started.md) and the guide for the app you will touch.
2. Check what branch you are on; the project convention is `main` (production-ready),
   `develop` (integration), `feature/*`, `bugfix/*`. Short-lived branches are normal.
3. Run `pnpm install` at the root, not inside an app — workspace linking matters.
4. Confirm the API answers on `/v1` and Swagger loads before changing anything.

## 2. Code style

| | Backend | Frontend |
| --- | --- | --- |
| Formatter | Prettier (`singleQuote: true`, `trailingComma: "all"`) | Prettier available (no repo config) — match surrounding files |
| Linter | ESLint + `@typescript-eslint` + Prettier plugin | `eslint-config-next` (flat config) |
| TS strictness | **Relaxed**: `strictNullChecks: false`, `noImplicitAny: false` | **Strict**: `strict: true` |
| Module system | CommonJS, decorators on | ESM/bundler resolution, `@/*` alias |

Because the backend disables `strictNullChecks` and `noImplicitAny`, the compiler will not
catch `undefined` dereferences or implicit `any` in services. Defend with runtime guards and
explicit types in new code; do not widen types to silence the IDE.

Other conventions:

- Conventional commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`), imperative mood.
- Prefer named exports in frontend modules; default exports only for Next pages/layouts.
- No new global CSS. Tailwind utilities + `components/ui` primitives only.
- No `console.log` in committed backend code — use `Logger`.
- Do not reformat whole files in a feature PR; it buries the diff.

## 3. Testing

**Current state (verified):**

- Backend: 68 `*.spec.ts` files, all generated by the Nest CLI and containing only
  `expect(service).toBeDefined()`. One e2e harness in `test/`.
- Frontend: no test runner, no test script, no test files.

That means `pnpm test` is green but proves almost nothing. Treat it as a harness, not as
coverage.

**Where tests are worth writing first** (highest blast radius):

| Area | What to assert |
| --- | --- |
| `order.service#create` pricing | Flash vs product discount exclusivity; BOGO pooling and cheapest-free selection; coupon base excludes free units; free-delivery threshold uses the discounted subtotal; shipping minimum rejection |
| `PermissionGuard` | Method→action mapping, ancestor inheritance, inactive-role denial, unknown menu URL |
| `coupon.service.validateCoupon` | 410 for expired, 400 for not-yet-valid/inactive/cap reached |
| BOGO math (`applyBogoDiscount`) | `maxGroupsPerOrder`, multi-line pooling, unit never feeds two campaigns |
| Stock ledger | `order_sale`, `order_cancel`, `purchase`, `purchase_reversal` produce consistent before/after values |

Commands:

```bash
pnpm --filter germanbutcher-backend test
pnpm --filter germanbutcher-backend test:cov
pnpm --filter germanbutcher-backend test:e2e
```

If you add a frontend test runner, prefer Vitest + Testing Library and cover the cart and
checkout summary math — those are the client-side computations most likely to disagree with
the server.

## 4. Definition of done

**Backend change**

- [ ] DTO validation + `@ApiProperty` on new fields
- [ ] Swagger decorators (`@ApiOperation`, `@ApiQuery/@ApiBody`, response type)
- [ ] Guards + `@ModulePermissions('<menu url>')` on admin routes
- [ ] `{ message, statusCode, data }` envelope, pagination metadata for lists
- [ ] Audit columns (`createdBy`/`updatedBy`) populated from `req.user`
- [ ] Money handled as decimal + rounded; no float arithmetic
- [ ] Cache decorators only on non-personalised endpoints
- [ ] Real unit tests for the new logic
- [ ] Env vars documented in [01](01-getting-started.md) if you added any

**Frontend change**

- [ ] Server component by default; `"use client"` only where needed
- [ ] Data through `utils/api-utils.ts`, not raw `fetch`
- [ ] `revalidatePath`/`revalidateTag` after mutations
- [ ] Loading, empty and error states
- [ ] Mobile layout checked (storefront bottom bar, admin sidebar collapse)
- [ ] No `localStorage` access during render
- [ ] New admin screen has a `menu` row + permissions, otherwise it is invisible

**Schema change**

- [ ] Entity updated, module registered with `forFeature`
- [ ] Production path is additive; SQL script written and archived with the release
      (see [05 §2](05-database.md#2-schema-change-policy))
- [ ] `database.dbml` refreshed (or explicitly noted as out of date)
- [ ] [05 Database](05-database.md) updated for new invariants

**Docs**

- [ ] Contract changes (route, envelope, cookie, env key, cache behaviour) reflected in the
      matching document in the same pull request

## 5. Review checklist

Reviewers should be able to answer yes to:

1. Does the change keep the money pipeline deterministic (order of discount application
   unchanged, or documented if changed)?
2. Are new admin endpoints guarded **and** backed by a menu row?
3. Does anything new cache personalised data?
4. Is every new query bounded (pagination, `take`, indexed filter)?
5. Are decimal columns converted with `Number()` before arithmetic?
6. Does the frontend handle a 401 and an API outage without a blank screen?
7. Are new environment variables documented and defaulted?
8. Is the diff free of unrelated reformatting and debug logging?

## 6. Known technical debt

Ordered roughly by risk. Each item is verifiable in the repository; none is hypothetical.

| # | Item | Evidence | Suggested fix |
| --- | --- | --- | --- |
| 1 | Order creation is not transactional | `order.service.ts#create` saves each product, writes stock movements, then saves the order; coupon re-validation runs **after** the stock loop, so a rejected coupon leaves stock decremented with no order | Wrap in `dataSource.transaction`; move validation before any writes and usage logs after commit |
| 2 | Test suite is scaffolding | 68 spec files with a single `toBeDefined()` assertion | Start with pricing + permission tests |
| 3 | No migrations | No `migrations/` directory; `synchronize` is the only schema tool, and the historical one-off scripts exist only in git history | Introduce TypeORM migrations before the next breaking change, and restore the operational SQL under `scripts/` |
| 4 | Manual payment-status endpoint ignores `paidAmount` | `updatePaymentStatus` updates only `paymentStatus` | Recompute from the ledger, or block manual edits when payments exist |
| 5 | Socket auth is trust-based | `notification.gateway.ts#handleConnection` reads `userId`/`isAdmin` from the query string | Verify a JWT in the handshake and derive rooms from it |
| 6 | Empty CORS list means "allow all" | `main.ts`: `origin: corsOrigins.length > 0 ? corsOrigins : true` | Fail closed in production when the list is empty |
| 7 | Stale schema snapshot | `database.dbml` misses `on_hold`, refund statuses, item price snapshots, CRM tables | Regenerate from a real database |
| 8 | Role-name spelling drift | `actions/auth.ts` accepts `modaretor`; `proxy.ts` accepts `moderator` | Standardise on one name and migrate roles |
| 9 | Mixed column naming | `attachment.gallery_id`, `address.user_id`, `category.isMainCategory` → `is_main_menu` | Documented in [05 §7](05-database.md#7-naming-inconsistencies-you-will-hit); rename only with a scripted migration |
| 10 | Throttling is in-memory and per instance | `ThrottlerModule` uses the default storage; no Redis; all buckets are keyed by IP, which is shared behind the Next server actions | Add a shared storage (Redis) or keys per user/session before scaling out |
| 11 | Guest-cart merge is not idempotent | `hooks/use-cart.ts` re-POSTs the whole local cart on every retry after a partial failure | Add a server-side merge endpoint (or upsert semantics) so retries cannot double-add |
| 12 | Operational SQL is only in git history | The working tree has no `apps/backend/scripts/`; `git log -- apps/backend/scripts` is the only way to find the repad/backfill scripts | Restore the scripts under `scripts/` or a `migrations/` folder |
| 13 | Unused dependency | `@aws-sdk/s3-request-presigner` is installed but no code calls `getSignedUrl` | Remove it (uploads use `PutObjectCommand` server-side) |
| 14 | Unused env keys | `API_PREFIX`, `MAX_FILE_SIZE`, `ALLOWED_MIME_TYPES`, `OTP_DEV_MODE`, `OTP_DEV_CODE`, `SMS_RETRY_ATTEMPTS`, plus the vestigial `bcrypt` entry in `allowBuilds` | Remove from `.env` / `pnpm-workspace.yaml` and docs, or wire them up |
| 15 | No CI | No `.github/workflows`, no other pipeline config | Add lint + build + backend tests on PR |
| 16 | Backend TypeScript is loose | `strictNullChecks: false`, `noImplicitAny: false` | Tighten per-directory, starting with `common/` and `order/` |
| 17 | Public debug endpoint leaks infrastructure | `GET /v1` returns the database host | Return `{ status: 'ok' }` instead |
| 18 | Analytics/audit retention asymmetry | Analytics configurable, audit fixed at 90 days | Make both configurable |

> `.dockerignore` also excludes `docs/`, so documentation is not present inside the built
> images. That is intentional (images stay small); read the docs from the repository.

Product decisions that look like bugs but are intentional:

- Coupon usage is capped globally, not per customer.
- Product detail pages bypass the Next.js data cache so deactivation is immediate.
- BOGO free units are blended into the line discount rather than added as cart lines.

## 7. Where things live

| Need to change… | Go to |
| --- | --- |
| An API route or guard | `apps/backend/src/<domain>/` |
| The order money rules | `apps/backend/src/order/order.service.ts` (top of `create`) |
| BOGO math | `apps/backend/src/bogo-campaigns/bogo-campaigns.service.ts` (`applyBogoDiscount`) |
| Coupon validation messages | `apps/backend/src/coupon/coupon.service.ts` |
| Free-delivery criteria | `apps/backend/src/free-delivery-campaigns/free-delivery-campaigns.service.ts` (`assessCampaign`) |
| Admin sidebar behaviour | `apps/frontend/components/admin/sidebar-menu.tsx` |
| Route protection | `apps/frontend/proxy.ts` |
| Cookie/session shape | `apps/frontend/actions/auth.ts` |
| Fetch/caching policy | `apps/frontend/utils/api-utils.ts` |
| Theme tokens | `apps/frontend/app/globals.css` |
| Docker/runtime | `Dockerfile.*`, `docker-compose.yml`, `next.config.js` |

## 8. Documentation maintenance

- `docs/` is the engineering source of truth; the root `README.md` is the front door.
- When code and docs disagree, fix one of them in the same PR — do not leave the conflict
  for the next reader.
- Prefer specifics (file paths, status codes, defaults) over narrative. Every rule in these
  documents should be checkable against the code in under a minute.

## Approach

The repository is a Node.js monorepo managed with **pnpm workspaces**. There is no root `package.json` dependency graph — the root manifest only declares workspace-scoped scripts that delegate to each app via `pnpm --filter`. Each application (`apps/backend`, `apps/frontend`) owns its own `package.json` and `pnpm-lock.yaml`, so third-party dependencies are declared per-app rather than hoisted into a shared workspace package.

## Key Files

- `package.json` (root) — workspace orchestration scripts (`dev`, `build`, `docker:*`) using `pnpm --filter`; no runtime dependencies here.
- `pnpm-workspace.yaml` — declares `packages: ['apps/*']`, plus pnpm policy overrides for native builds and Next.js release age.
- `apps/backend/package.json` — NestJS 11 backend dependencies (TypeORM, AWS SDK v3, Passport, Swagger, etc.).
- `apps/frontend/package.json` — Next.js 16 frontend dependencies (Radix UI, TipTap, Tailwind v4, React 19).
- `pnpm-lock.yaml` (root) — deterministic lockfile generated by pnpm; also present under each app directory.

## Architecture and Conventions

**Workspace layout.** The workspace config lists only `apps/*`, meaning there are no shared internal packages (no `libs/` or `packages/` scope). Backend and frontend are independent npm packages with their own dependency trees.

**Version ranges.** Dependencies use caret (`^`) ranges in both apps, allowing minor/patch updates within the major version. A few exceptions exist:
- `next` is pinned exactly at `16.4.3` in the frontend.
- `react` / `react-dom` use `^19.3.0`.
- `multer` uses the LTS tag `1.4.5-lts.2`.
- `@nestjs/mapped-types` uses bare `*`.

**Native addon handling.** `pnpm-workspace.yaml` explicitly enables native build support for four packages via `allowBuilds`: `@scarf/scarf`, `bcrypt`, `sharp`, `unrs-resolver`. This is necessary because pnpm's default behavior blocks native addons from building during install.

**Next.js release-age bypass.** The `minimumReleaseAgeExclude` section exempts all `@next/swc-*` platform binaries and `next@16.4.3` from pnpm's minimum release age check, allowing the exact pinned Next.js version to be installed even if it is considered "too new" by pnpm's registry heuristics.

**Lockfiles.** A single `pnpm-lock.yaml` lives at the repo root and covers the entire workspace. No `.npmrc` file exists, so no private registry or authentication is configured — dependencies resolve from the public npm registry.

**No vendoring.** There is no `vendor/` directory or equivalent; node_modules are not committed (`.gitignore` patterns exclude them). Docker images are built separately via `Dockerfile.backend` and `Dockerfile.frontend`.

## Constraints and Rules

- Workspace membership is enforced by `pnpm-workspace.yaml` listing only `apps/*`; adding packages outside this glob will not participate in the workspace.
- Native addons must be whitelisted in `allowBuilds` in `pnpm-workspace.yaml` to build successfully under pnpm (enforced by pnpm itself).
- The Next.js 16.4.3 dependency tree requires the explicit `minimumReleaseAgeExclude` entries in `pnpm-workspace.yaml`; without them, pnpm would reject those releases as too new.
- Scripts in the root `package.json` require pnpm (they invoke `pnpm --filter ...`); running with npm/yarn will fail.
